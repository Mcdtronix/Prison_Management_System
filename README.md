# 🏛️ Prison Management System (PMS) — Enterprise System Architecture & Technical Overview

---

## 1. Executive Summary & System Philosophy

The **Prison Management System (PMS)** is an enterprise-grade, full-stack, multi-tenant facility and inmate lifecycle management platform designed for national correctional authorities. It enforces strict **3-tier organizational data isolation** (National HQ → Provincial Commands → Individual Stations/Prisons) alongside granular **Role-Based Access Control (RBAC)**, precise calendar-based sentence computation, and auditable operational workflows.

The system is architected as a **decoupled, stateless RESTful backend** built on Django 5.2 and Django REST Framework (DRF), backed by **PostgreSQL** for relational ACID compliance, paired with an interactive **Single Page Application (SPA)** engineered with React 18, TypeScript, and Vite.

---

### Backend Micro-Architecture
* **Framework**: Django `5.2.11` + Django REST Framework (`3.15+`)
* **Database Driver**: `psycopg2-binary` (PostgreSQL interface)
* **Auth Engine**: JWT via `djangorestframework_simplejwt`
* **Date Arithmetic Engine**: `python-dateutil` for strict exact-calendar computation
* **API Documentation**: OpenAPI / Swagger (`drf-yasg`)

### Frontend Architecture
* **Core**: React `18.x` with strict TypeScript `5.0+`
* **Build System**: Vite
* **State & Server Data Fetching**: TanStack React Query (`v5`)
* **Form Engine & Schema Validation**: `react-hook-form` + `zod`
* **Design System**: TailwindCSS + Radix UI primitives (Shadcn UI architecture) + Lucide Icons
* **Data Visualization**: Recharts

## 3. Core Architectural Patterns & Design Principles

### 3.1 3-Tier Multi-Tenant Hierarchical Model

The foundational domain model enforces a strict 3-tier organizational structure across the entire application:

```
                          ┌───────────────────────────┐
                          │   National HQ (Level 1)   │
                          │ System Policy & Governance│
                          └─────────────┬─────────────┘
                                        │
                         ┌──────────────┴──────────────┐
                         ▼                             ▼
           ┌───────────────────────────┐ ┌───────────────────────────┐
           │ Provincial HQ 1 (Level 2) │ │ Provincial HQ 2 (Level 2) │
           └─────────────┬─────────────┘ └─────────────┬─────────────┘
                         │                             │
          ┌──────────────┴──────────────┐              └──────────────┐
          ▼                             ▼                             ▼
┌──────────────────┐          ┌──────────────────┐          ┌──────────────────┐
│ Station A (Lvl 3)│          │ Station B (Lvl 3)│          │ Station C (Lvl 3)│
└──────────────────┘          └──────────────────┘          └──────────────────┘
```

1. **National HQ (`NATIONAL_HQ`)**: Governance, system-wide analytics, national rollouts, and audit supervision.
2. **Provincial Command (`PROVINCIAL_HQ`)**: Regional monitoring, inter-station transfers, and provincial staff management.
3. **Station (`STATION`)**: Daily ground operations including inmate intake, cell assignment, medical OPD visits, feeding logs, and store inventories.

### 3.2 Granular Data Isolation & Scoping Engine

Every root domain entity (`Inmate`, `Patient`, `OfficerPosting`, `StockReceipt`, `FarmProject`, `Message`) holds an `owner_org_unit` foreign key to `OrgUnit`.

* **Automatic Query Scoping**: Custom DRF permission classes (`IsStationUser`, `IsProvincialUser`, `HasOrgUnitPermission`) and queryset filters automatically isolate records based on the authenticated user's active `UserAssignment`.
* **Controlled Upward Data Exposure**: Top-down access is blocked by default. High-tier access is permitted only through explicit **Data Exposure Policies** (`DataExposurePolicy` & `DataExposureRecord`), enabling audited upward data visibility for regional or national reporting without breaching station-level data boundaries.

---

## 4. Primary Subsystems & Domain Modules

### 4.1 Inmate Reception & Lifecycle Engine (`Reception/`)
* **Intake & Biometrics**: Registers personal identification, aliases, emergency contact data, next-of-kin, physical attributes, and intake photos.
* **Offence & Sentence Tracking**: Supports multi-offence charges, sentence types (determinate, life, fine-default), bail terms, and court dates.
* **Reclassification & Cell Allocations**: Tracks security classifications (Maximum, Medium, Minimum) with periodic reclassification schedules.
* **Discharge Management**: Handles sentence expiration, court acquittal, presidential pardon, bail release, and conditional parole processing.

### 4.2 Exact-Calendar Sentence Computation Engine
The system contains an specialized mathematical sentence calculation engine (`python-dateutil` integration) designed to prevent release-date calculation errors:
* Calculates **Ordinary Date of Release (ODR)** and **Earliest Date of Release (EDR)** incorporating earned remission (e.g., standard 1/3 sentence reduction rules).
* Seamlessly handles leap years, month-length variations, concurrent vs. consecutive sentence aggregation, and time spent in pre-trial custody.

### 4.3 Health & OPD Services (`Health/`)
* **Admission Medical Assessment**: Initial medical screening (TB, HIV, chronic conditions, psychiatric history, physical injuries) conducted upon intake.
* **Outpatient Department (OPD)**: Daily clinic register tracking complaints, diagnoses, prescribed medications, and referrals to external hospitals.
* **Discharge Medical Audit**: Ensures health clearance before an inmate is released or transferred.

### 4.4 Human Resources & Staff Management (`HumanResources/`)
* **Officer Profiles**: Ranks, service numbers, specialization tags, qualifications, and employment history.
* **Postings Engine**: Tracks deployment history (`OfficerPosting`) across organizational units over time.
* **Station Roster & Departmental Assignment**: Scopes officer roles to specific operational departments (e.g., Reception, Stores, Medical, Administration).

### 4.5 Stores, Inventory & Logistics (`Stores/`)
* **Stock & Inventory**: Commodity management (uniforms, rations, medical supplies, hardware).
* **Feeding Session Logs**: Tracks daily dietary distributions and per-capita inmate feeding counts against inventory drawdowns.

### 4.6 Inter-Departmental Messaging (`Messaging/`)
* **Organizational Mailboxes**: Maps communication channels to department mailboxes (e.g., `Reception@HarareCentral.pms`).
* **Threaded Communication & Auditing**: Facilitates official multi-station communication with read receipts, attachments, and draft management.

---

## 5. Security Architecture, RBAC & Compliance

### 5.1 Multi-Assignment Identity Model
Users (`Auth.User`) are decoupled from static roles. Access is controlled via `UserAssignment` entries binding a user to:
* An **Organizational Unit** (`OrgUnit`)
* A **Department** (`Department`)
* A specific **Role** (e.g., `STATION_ADMIN`, `RECEPTION_OFFICER`, `HEALTH_OFFICER`, `STORES_OFFICER`, `NATIONAL_SUPERVISOR`)

Users can hold multiple assignments across facilities or roles, but execute actions under a single active context at runtime.

### 5.2 Audit Trails & Regulatory Compliance
* **Immutable Logs**: State-changing actions record `created_by`, `created_at`, `updated_at`, `revoked_by`, and `revoked_at`.
* **Database Constraints**: Enforces structural validity at the DB level via SQL check constraints (e.g., hierarchy logic checks preventing a Station from being assigned as a parent to a Province).
* **Custom Audit Middleware**: `Core.middleware.AuditLogging` captures endpoint accesses, HTTP methods, IP addresses, payload summaries, and user contexts for auditing.

---

## 6. Frontend Architectural Highlights

* **Role-Adaptive Interface**: The React SPA uses custom hooks (`useAuth`, `usePermissions`) to dynamically update sidebars, action triggers, and operational dashboards depending on whether the user is logged into a Station, Provincial, or National context.
* **Form Resilience & Validation**: Form logic leverages `react-hook-form` paired with strict `zod` schemas, providing instant client-side feedback on complex multi-step forms (e.g., inmate intake, sentence recording, medical evaluations).
* **Optimistic UI & Cache Management**: TanStack Query provides instant UI transitions and handles API caching, background refetching, and query invalidation.

## 7. Developer Quick Start & Commands

### Backend Setup
```bash
# Clone the repository
git clone https://github.com/Mcdtronix/Prison_Management_System.git
cd Prison_Management_System

# Activate environment & install requirements
source env/bin/activate  # On Windows: env\Scripts\activate
pip install -r requirements.txt

# Run migrations & launch server
python manage.py migrate
python manage.py runserver 0.0.0.0:8000
```

### Frontend Setup
```bash
# Navigate to frontend root
cd Prison_Management_System/Frontend

# Install dependencies & run Vite dev server
npm ci
npm run dev
```
